# Adopt a survivor project

The fifteen-minute quickstart validates the workflow tool. A complete survivor
requires C#/BepInEx/R2API integration and playtesting; this scaffold does not
promise a playable character in fifteen minutes.

For the smallest concrete integration, start with the original
[native survivor recipe](../examples/first-survivor/README.md). It provides the
body/master/display/content registration, stock skills, exact build references,
resolved lock and complete package mappings. Its optional build-only adapter
has an actual compile receipt. Native acceptance is still a separate gate.

For an existing survivor, use `init` in a **new sibling directory**, then copy
only the generic files you want into your project after reading existing
instructions. Never overwrite an existing AGENTS.md, license or manifest.
Merge instructions consciously and give shared files to one integrator.

For a new survivor, choose a community framework with a verified license. The
[character wiki](https://risk-of-thunder.github.io/R2Wiki/Mod-Creation/Assets/Character/)
is a starting point, not permission to vendor a template. HenryTutorial is
useful prior art; no license for redistribution was verified during this review.
Link and learn rather than copying its implementation into this starter.

## Connect real inputs

1. Replace `plugin.source` and `plugin.version_constant` with your actual literal
   C# version constant. Add all relevant exact source/config/asset input files
   to `inputs` for evidence identity. Paths are portable and inside the project.
2. Replace `package` paths with your actual player-facing package metadata.
   Use plain numeric version parity, exact dependencies and an original icon.
   Source README and Thunderstore README serve different audiences.
3. Add each owned artifact to `files`, with `source`, `destination`, `sha256`,
   `license` and `provenance`. A real mod requires an owned DLL under `plugins/`
   and declared runtime dependencies. Bundle/bank/license records need entries
   too. A record's claim still requires a human rights/provenance review.
4. Run your reviewed build **without profile deployment**. Build Unity/Wwise
   assets separately with a serial editor owner. Record tool versions and
   actual input/artifact hashes. Workbench never builds them automatically.
5. Set `mode` to `mod` after integration. Run `pin`; inspect the new
   `local/workbench.pinned.json`, verify licenses/provenance and deliberately
   adopt it as `workbench.json`. Re-pin each change; no broad stale-input waiver.
6. Run `check --release`, package to a new ZIP, then independently `verify` it.
   The exact allowlist must match. Only after authorized clean-profile and
   physical/network acceptance should you consider publication.

Example additional file mapping (the null hash must be pinned before release):

```json
{
  "source": "mod/bin/Release/netstandard2.1/MySurvivor.dll",
  "destination": "plugins/MySurvivor/MySurvivor.dll",
  "sha256": null,
  "license": "MIT",
  "provenance": "Original project code; verify matching build receipt"
}
```

The CLI allows a declaration; it does not certify it. It cannot establish that
the assembly corresponds to your C# constant or that a bundle was rebuilt from
all current Unity inputs. Keep separate build and generated-asset receipts.

## Dependency and editor decisions

Consult current primary sources instead of copying historical pins. The
[Unity version page](https://risk-of-thunder.github.io/R2Wiki/Mod-Creation/Unity-Version/)
reports 2021.3.33f1 as of February 2026; confirm the installed game and project
version before opening a Unity project. Older tutorial versions are not a
default migration choice. Unity security and patched editor compatibility need
their own review, rather than a blind editor upgrade.

[R2API](https://github.com/risk-of-thunder/R2API) uses split modules. Declare only
the needed NuGet references and Thunderstore dependencies; their version
numbers are not interchangeable. Resolve/pin the actual build graph. The
[official ExamplePlugin](https://github.com/risk-of-thunder/ExamplePlugin)
illustrates current references, but floating versions in examples are not a
tested release lock. Keep game/framework DLLs external, never in the ZIP.

Use a vanilla body/stock assets by in-game reference for the first skill.
Do not export game asset bytes into this public starter. Modern
ContentManagement catalog additions happen before catalog initialization;
PrefabAPI clone/network registration behavior should be checked against the
chosen revision. Those integration APIs are not generated by this v0.1.
